# CRM acceleration phase 1: independent Shopify full-history export

## Scope and safety

- `api/crm-orders-bulk.js` is an independent, CRON_SECRET-protected endpoint; this extracted review branch **does not register a new Vercel cron**, and it does not alter CRM customer records or grades.
- Requires the Vercel Shopify synchronization application's `read_orders`, `read_all_orders`, and `read_products` scopes. This is **not** the Feishu bot's token.
- Starts an asynchronous Shopify Bulk Operation, polls by its ID and archives the completed JSONL response into a private Vercel Blob. Operation state and raw export use versioned keys separate from existing 180-day snapshot and reconciliation.
- The Bulk operation is designed to export every available historical order (no 180-day date filter), line-item sale-time prices and current product metadata. Deleted products may have null metadata; this must not remove the historical order line.
- The original JSONL archive uses a **no-overwrite private Blob write** (`allowOverwrite:false`). If the checkpoint is missing but an archive already exists, return `409 bulk_archive_exists_without_checkpoint` and require an operator to reconcile the private state and Shopify Bulk ID. A transient/non-404 checkpoint read must fail closed, not trigger a second Bulk run. If a retry collides with an existing archive, preserve the old checkpoint and do not overwrite the JSONL; recovery is manual and requires verifying the existing archive. Never delete the raw archive, reset a cursor or silently rerun a completed historical export.
- The raw archive is **not yet a validated financial ledger**. `totalRefundedSet` is only one raw aggregate; do not infer item-level net revenue by subtracting it from a merchandise subtotal. The next phase must reconcile refunds/transactions, currencies, cancellation, test orders and customer IDs before updating final M/F/R or LTV.
- `api/crm-orders-bulk-audit.js` separately scans the private JSONL export, deduplicates order IDs, checks child-parent linkage, excludes invalid orders, and flags discrepancies between successful refund transactions and Shopify's refunded total. This report is intentionally audit-only and may be incomplete for multi-currency/custom refunds; it never changes Feishu CRM customer fields.
- No scheduled Shopify full-history export is installed by this review branch. The endpoint **will not launch or poll an export** unless the runtime is explicitly `VERCEL_ENV=production` **and** the server-only `CRM_FINANCE_BULK_ENABLED` is exactly `true`. Preview, Development and missing stage markers cannot start the export even if the opt-in flag is accidentally copied. With the variable absent (the expected Draft/UAT state), its CRON_SECRET-protected endpoint returns `paused: bulk_requires_explicit_approval` without requesting Shopify scopes or touching any Blob. Enabling requires explicit merchant approval and separate pre-release QA; `READY` alone is not approval. Completed jobs are idempotently reported and not relaunched. Failed/cancelled jobs require investigation and do not silently restart.
- This extracted review branch inherits `vercel.json` **unchanged from production main**. It does not remove, restore, add or reconfigure any scheduled jobs. Historical Gmail cron retirement, if warranted by a fresh `finished=true` checkpoint, is a separate approval.

## Gmail efficiency

Gmail email-index caching from the original PR #4 is deliberately **excluded** from this finance-only extraction. The current main's Gmail routines and checkpoints remain untouched.

## Verification after deployment

1. Before enabling `CRM_FINANCE_BULK_ENABLED`, confirm the existing completed Gmail historical import checkpoint is `finished=true`, recheck Vercel production cron, verify the authorized API returns `bulk_requires_explicit_approval` while the gate is absent, then obtain merchant approval. Check `/api/crm-shopify-health` and ensure all required scopes, including `read_products`, are reported; the exporter remains paused when absent.
2. Once separately authorized, inspect the authenticated endpoint phase transitions: `started` → `running` → `archived` with a nonzero root order count; do not enable a recurring cron without separate approval. Do not expose signed export URLs.
3. Verify the versioned private archive includes order rows plus JSONL child rows linked using `__parentId`, and compare order counts to Shopify analytics. Check whether the export is large enough to require a separate durable downloader; 85-second download timeout is fail-and-retry, not data loss.
4. Test the seven customer IDs in the merchant's Shopify 180-day >$3,000 segment against the raw order ledger before trusting any CRM grades.
5. Do not run final grade reconciliation until the all-history ledger and refund semantics are validated.

See Shopify docs: https://shopify.dev/docs/api/usage/bulk-operations/queries

## Seven-customer high-value financial sample (Draft, audit only)

- Set server-only \`CRM_FINANCE_SAMPLE_CUSTOMER_IDS\` to seven unique Shopify customer GIDs separated by commas. These must come from the merchant-approved seven high-value accounts, **not** guessed from 180-day M or generated by the dashboard. Never expose this setting in frontend code, issue comments, logs or static assets.
- The CRON_SECRET-protected \`/api/crm-orders-bulk-audit\` reads the private JSONL once, records each selected customer's order IDs, order dates, inclusion/exclusion reasons, refund evidence, historical merchandise net and rolling 180-day amounts, and archives results in a **private Blob**. No CRM tier or Feishu write occurs.
- `sampleAudit.status` is BLOCKED when seven Shopify sample IDs, per-customer source order counts, original order IDs, refund reconciliation or settled payment/currency evidence are incomplete, or when duplicates / over 100 evidence rows occur. `BLOCKED_SAMPLE_REFUND_RECONCILIATION` and `BLOCKED_SAMPLE_FINANCIAL_EVIDENCE` prevent financially inconsistent samples from appearing manual-ready. Otherwise the sample stays `PENDING_MANUAL_SHOPIFY_FINANCIAL_RECONCILIATION`. `sampleAudit.verified` remains false throughout.
- A reviewer must cross-check each of the seven against original Shopify order totals, currency, refunds, returns, order status and fulfilled product lines.
- Every selected customer's raw historical order must have a verifiable creation timestamp on or before the audit `asOf`, even when the order is cancelled, a test order, refunded or otherwise excluded from M/F. A missing, impossible or future date sets `invalidOrderDates` and `BLOCKED_SAMPLE_ORDER_DATE_EVIDENCE`; it is not silently counted as complete sample evidence. The source JSONL may itself be incomplete due to the Shopify Bulk API, so a full-export count comparison and permissions review are also mandatory.
- Transaction refund totals and \`totalRefundedSet\` may differ for legitimate shipping/tax, currency and gateway adjustments. Mismatch is an audit signal, **not** proof of fraud or a basis for automatic customer regrading.
- Refund transactions exceeding the order's verified successful SALE/CAPTURE amounts are quarantined as `refund_exceeds_captured`, causing `BLOCKED_REFUND_RECONCILIATION` even for fully refunded orders. This requires original Shopify/gateway evidence; it is not a fraud determination.
- If the sample is blocked, leave production RFM and customer grade unchanged. This extracted Draft has no production deployment, no new cron, and no merchant approval to trigger the export.
- A count-complete JSONL archive is **blocked** when any settled positive-merchandise order has zero associated child line items, even when root/total Shopify object counts match. This prevents accepting a partial product graph as complete evidence. The seven-account sample separately reports `BLOCKED_SAMPLE_MISSING_LINE_ITEMS`; no grade or RFM write is authorized.
